# Changelog

## 2.0.0

For **protocol version 2** of the stats pipe. Breaking: a client of version 1.x cannot read a protocol 2 game, and this library refuses a game of protocol 1.

- **Breaking, the wire envelope.** Frames from the game now have a 17 byte little-endian header: `u32 body length | u8 type | u32 sequence | u64 timestamp_us`. Frames to the game keep the 5 byte header. `RawFrame` is now `(type, sequence, timestampMicros, body)` (the old two-argument constructor still exists for synthesized frames, with sequence 0 and timestamp 0); `DecodedFrame` has `sequence()` and `timestampMicros()` and `wireBytes()` counts 17 header bytes. The new frame types are `0x09 Hello` and `0x0A Response` from the game and `0x11 Request` to the game (`FrameType.HELLO`, `RESPONSE`, `REQUEST`).
- **Breaking, the handshake.** The first frame of a connection must be the game's `Hello` with `protocol_version` 2. `StatsPipe` waits for it (`helloTimeout`, 10 s by default) and refuses another version (`ProtocolVersionException`), another first frame (`FrameException`) and silence (`HelloTimeoutException`); the cause is passed to `onDisconnected`. New: `StatsPipe.hello()`, `awaitHello(Duration)`, `hasCapability(String)`, `StatsListener.onHello`, `MatchState.hello()` / `hasCapability`, `StateListener.helloReceived`, and the helper class `Handshake`.
- **Dropped frames.** The sequence numbers are checked on every connection (and on dump replays) with unsigned 32 bit arithmetic: `StatsPipe.droppedFrames()`, `MatchState.droppedFrames()`, `StatsListener.onFramesDropped(long)`, `StateListener.framesDropped(long, long)`. `ClockSync` (`StatsPipe.clockSync()`) estimates the offset between the game's frame clock and the local one and the extra delay of a frame; `Handshake.wallClockMillis` converts a timestamp with `Hello.epoch_unix_ms`.
- **Requests.** `StatsPipe.request(Request, Duration)` returns a `CompletableFuture<Response>` (ids assigned by the library, matched by id, `RequestTimeoutException` after the timeout, all pending requests fail with an `IOException` when the connection ends or the pipe closes, late and unknown responses ignored, no requests before the Hello). Typed methods: `catalog`, `object`, `objects`, `player`, `map`, `resync`, `feedConfig`, `setFeedConfig`, which fail with `RequestFailedException` (the `ResponseStatus` and the game's message) for any status but OK, and the paging helpers `catalogAll` / `objectsAll` (follow `next_cursor`, at most 100 pages, `PageLimitException`). The game rate-limits requests (`Hello.max_requests_per_second`, `max_request_burst`) and answers `RATE_LIMITED`; `StatsPipe.Builder.limitRequests(true)` applies the same limit on the client (off by default). New builder options `helloTimeout` and `requestTimeout`. `StatsListener.onResponse` sees every response.
- **Several readers.** The game serves up to `Hello.max_readers` readers per pipe; the library needs nothing for it, `reader_slot` and `max_readers` are in the Hello. The docs no longer say "one reader per pipe".
- **Dump files.** `DumpWriter` writes a header (magic `GOSD`, format version 2) and every frame with its sequence number and timestamp, the Hello included; `DumpReader` replays it and reports gaps as dropped frames. Dumps of format version 1 (no header, 5 byte envelope) are still read, with consecutive sequence numbers and timestamp 0. A dump of any other version is refused with a message saying so. `DumpWriter.FORMAT_VERSION` is 2.
- **Events.** The `StatEvent` message has `object_id`, `killer_object_id`, `killer_template` and `weapon` (generated classes); `Format.eventDetail` describes the killer and weapon of kills and losses.
- The test client shows the Hello (game version, protocol, reader slot of the maximum, logic rate) and the dropped-frame count in the GUI status area, prints `HELLO` and `DROPPED` lines in `watch` and `replay`, and adds `dropped N` to the `dump` status line. The `schema` command lists the new frames. The examples say the game serves several readers; their jar names are now 2.0.0.

## 1.0.0

First release of `com.generalsonline:stats-pipe-client`.

- The library (`lib/`): `StatsPipe` (builder, auto-discovery of running games preferring a free one, reconnect with backoff, an executor for the callbacks, `sendChat` with the documented limits), `StatsListener` (one method per frame type, lifecycle, errors), `MatchState` with `StateListener` change callbacks (players joined with MatchInfo, light/full snapshot merge, player state, match lifecycle, camera, world extent and map-level data, bounded event and chat buffers), `DumpWriter`/`DumpReader` with replay paced by game time, and the `Format` helpers. Generated protobuf classes come from the engine's `StatsExporter.proto`. Javadoc on every public type and member.
- The test client (`app/`), now written against the library's public API only: the commands `watch`, `dump`, `replay`, `chat`, `gui`, `schema` and the new `example`; the GUI with the tabs Players, Minimap, Events, Chat, Lobby, Match, Frames and the new Code tab.
- The example-code generator: eight scenarios (print every frame, track a player's stat, react to an event kind, draw the camera view box, show the lobby with predicted factions, send a chat line, record and replay a dump, use the state from a UI thread), filled with the selected Players column, event kind or chat channel. Each template is compile-checked, and the programs are in `examples/`.
- Changed from the earlier single-project client: the packages are `com.generalsonline.stats` (API), `.proto`, `.internal` and, for the client, `.app`; `FrameListener` became `StatsListener` (with `onFrame` instead of a frame tap), `StatsPipeClient` became `StatsPipe`, `DumpFile` became `DumpWriter` and `DumpReader`.
