# Changelog

## 3.0.0

Breaking for source and build; the protocol is still version 2 and the wire format did not change. Everything that was in 2.4.0 (below) is part of this release.

- **Java 11.** The library, the client and the examples compile with `--release 11` and need a Java 11 runtime instead of 17. Records, pattern matching for `instanceof`, switch expressions and text blocks are gone from the code; the public value types keep their accessor names (`PlayerView.name()`, `DecodedFrame.type()`, ...) but are now final classes, so they no longer are `java.lang.Record`s (no `RecordComponent` reflection, no deconstruction); `equals`, `hashCode` and `toString` behave as before. The generated example programs need nothing newer than Java 11 either. protobuf-java is still the library's only dependency.
- **`FakeGame` is removed**, with `FakeDump`, `FakeFeed`, `FakeWorld`, `FakeCamera`, `FakeSynth`, `FakeLobby` and the internal in-memory link and PowerShell pipe server. To try a tool without a game, replay a dump (`DumpReader`, `gui --replay`) or run it against a real game. `StatsPipe` lost its package-private test hooks (the pipe opener, the candidate supplier) and talks to `NamedPipeLink` directly; `PipeLink` is gone.
- **Tests are removed**: `lib/src/test`, `app/src/test`, the JUnit dependencies and the `examples.dir` wiring of the Gradle files.
- **Test client.** The `serve` command, `gui --fake`, the `fake-server` example scenario (and `FakeServer` in `examples/`, and `example --dump`) are removed. The `gui --replay` window stays.
- **A new look for the window.** A dark theme on FlatLaf 3.5.4 (the client's only dependency besides the library; the library has none) with the design in one place (`Theme`, `Ui`): a header strip with the connection state light, screen, match, game time, speed and dropped frames; a navigation rail that groups the twelve sections; banners for a stale feed and a finished match; tables with right aligned numbers, zebra rows, player colours as chips and names, and empty states that say what to do; cards and aligned forms for the Camera, Lobby, Director and Query sections that wrap at narrow widths; success, warning (the game's NOT ALLOWED, in bold amber) and failure lines in one style; a minimap on a dark ground with a grid and a legend. Every section, right-click menu, column view, filter, stat card, "Show code for this" and director tunable works as before.
- **Camera control in any match.** The game no longer gates camera and follow commands: they work in any running match, also for an active player; observing a player still needs an observer or a replay, replay control a replay. The wording of the library javadoc, the window, the examples and the README follows.
- **Recording in the window.** A Record and Stop control in the header writes the live feed to `Documents\GeneralsOnline\Recordings\<date>-<map>.dump` (never overwriting), with the time and size while it runs; Recordings opens a recording or one of the newest, and the window then plays it with play and pause, a speed and Back to live. A recording is a library dump, not a game replay (.rep).
- **Chat** is a conversation view with a tab and an unread count per channel, player colours, search, scroll-lock, and a composer that offers only the channels the game delivers to now (1024-byte counter, history, quick lines, echo confirmation). **Control** is a section for casters: replay transport, observe buttons in player colours, follow selection, eight camera positions, the director, and keyboard shortcuts.
- **Settings section** (connection, the feed settings the game applies per connection, re-sent on every connect, the recordings folder, the opening section and the inspector default, about the game), the object inspector follows the selection in the game, a team summary above the Players table, "Every frame" light snapshots with coalescing on the event thread.

- The examples and the README name the 3.0.0 jar.

## 2.4.0

Additive; the protocol is still version 2.

- **Every-frame light snapshots.** `light_interval_ms` now goes down to 1, which means a light snapshot every logic frame (`StatsPipe.LIGHT_EVERY_FRAME`). Older game builds answer `BAD_REQUEST` below 50. The full snapshot keeps its floor of 100 ms. `local_logic_fps` is now measured over at least 250 ms, so it stays steady at any cadence.
- `FakeGame` accepts the same range.
- The examples and the README name the 2.4.0 jar.

## 2.3.0

Additive; the protocol is still version 2 and nothing of 2.2.0 changed incompatibly. A game without the capability `lobby.control` answers the new request `BAD_REQUEST`.

- **Lobby control.** `StatsPipe.lobbyControl(LobbyControlQuery)` and the typed methods `openSlot`, `closeSlot`, `addAi`, `kickPlayer`, `setFaction`, `setColor`, `setTeam`, `setStartPosition`, `changeMap`, `setStartingCash`, `limitSuperweapons`, `setLobbyGameSpeed`, `acceptLobby` and `startGame` change the game setup lobby the user sits in (skirmish, LAN, Generals Online) by operating the setup screen's own controls, so the screen's rules decide: a refusal arrives as a `NotAllowedException` with the reason, a bad argument as a `RequestFailedException` (`BAD_REQUEST` or `NOT_FOUND`), no setup screen as `UNAVAILABLE`. The answer (`LobbyControlResult`) names the lobby kind and whether the change was `APPLIED`, `REQUESTED_FROM_HOST` or `REQUESTED_FROM_SERVICE`. `LobbyControl` builds the actions (`LobbyControl.AiLevel` has `EASY`, `MEDIUM` and `BRUTAL`, the screen's Hard). New proto messages `LobbyControlQuery` (request field 21), `LobbyControlResult` (response field 21), `LobbyKick`, `LobbyPress`, `LobbyChangeRoute`; Hello capability `lobby.control`.
- **`FakeGame`** accepts lobby control while its dump is in a game setup lobby, by the rules of the setup screens (the host changes slots, map and rules, a client its own slot and accepts), sends the changed `LobbyState` to every reader and answers `UNAVAILABLE` outside a lobby. `Builder.lobbyLocalSlot(int)` makes the local user a client. The Hello lists `lobby.control`.
- **Test client.** The Lobby tab has the lobby controls (slot actions, faction, color, team, start position, map, starting cash, superweapon limit, skirmish speed, Accept and Start) with the game's `NOT_ALLOWED` shown in orange like the Camera tab, and a right-click menu on a slot (open, close, kick, add an AI of each level). New scenario `lobby-control` in the Code tab, the `example` command and `examples/` (`ControlLobby`).
- The examples and the README name the 2.3.0 jar.

## 2.2.0

Additive; the protocol is still version 2 and nothing of 2.1.0 changed incompatibly.

- **`FakeGame`**, a stand-in for a running game: it serves a dump file as the stats pipe of a game, so tools and the `Director` can be developed offline. It sends a Hello (reader slot, limits, the capabilities), re-sequenced and re-timestamped frames paced by game time with a speed factor, optionally looping, to up to four readers that join live, honors each reader's feed configuration (cadences, camera, events, chat, view statistics, interest, the heavy parts of full snapshots), and answers the requests from a model built from the dump: catalog (paged), objects, players, the map (with a generated minimap image), resync and feed configuration, with `NOT_FOUND`, `UNAVAILABLE`, `BAD_REQUEST` and `RATE_LIMITED` where the game has them. Camera, follow, replay and observer commands are accepted by the rules of a `Situation` (`REPLAY`, `OBSERVER`, `PLAYER`, which gives `NOT_ALLOWED`) and reflected: a camera model with transitions, locks that follow the dump's unit positions and end when the unit dies, `Camera` frames with change source `PIPE`, pause and speed that change the pace. `simulateUserCameraInput()` plays a human taking the camera. A dump without view statistics or interest frames gets plausible stand-ins computed from its snapshots and events. See the README, "The fake game".
- **Two transports.** A real Windows named pipe (`\\.\pipe\generalsonline-stats-<pid>`, found by discovery like a game; hosted by a hidden Windows PowerShell process because Java cannot create one; Windows only) and an in-memory connection (`FakeGame.connect(StatsPipe.Builder)`, any system).
- `Director.lastMove()`: the last move the director sent, with its reason.
- **Test client.** The `serve` command (`serve <dump> [--speed x] [--loop] [--no-wait] [--pid n | --pipe name] [--situation s]`) and `gui --fake FILE`. New GUI tabs and panels: **Query** (a catalog browser with paging, an object inspector, player detail, the map with its minimap image, feed configuration and resync), **Camera** (camera, follow, replay and observer control with the game's `NOT_ALLOWED` shown plainly), **In view** (the view statistics per player with a share bar, notable units, superweapons in view, fight intensity), **Director** (mode, start and stop, tunables, state, last target and reason, paused-by-human banner), and on the **Minimap** an interest map overlay with a switch that turns the interest feed on and a list of pending highlights. Right-click **Inspect object** on an Events row (object and killer) and on a notable unit. The Match tab shows the game's Hello. **Show code for this** is wired into the new panels.
- **Code generator.** Seven new scenarios, each compiled warning-free by the tests and present in `examples/`: `query-catalog`, `inspect-object`, `camera-control`, `replay-control`, `view-stats`, `director` and `fake-server`, filled from the new selections (template and side, object id, camera position and zoom, replay speed, director mode, dump file), also by the `example` command's new options.
- The examples and the README name the 2.2.0 jar.

## 2.1.0

Additive, for **protocol version 2** (unchanged): a 2.0.0 client keeps working against a game that has these features, and this library still works against a game that has not (the new frames never arrive, the new requests answer `BAD_REQUEST` or fail with a timeout; check the new capabilities in the Hello). Nothing was removed or changed incompatibly, so this is a minor version.

- **Camera control.** `StatsPipe.moveCamera(CameraMove)`, `resetCamera()`, `cancelCameraTransition()`, `cameraControl(CameraControlQuery)`: set any subset of position, zoom, angle and pitch, at once or over a wall-clock transition with `NONE` or `EASE_IN_OUT` easing, or reset angle, pitch and zoom to the game's defaults. `followUnit`, `tetherUnit`, `unfollowUnit`, `cameraFollow(CameraFollowQuery)`: lock the camera on a unit. `CameraMove` is an immutable value: `to`, `set`, `reset`, then `position`, `zoom`, `angle`, `pitch`, `over(Duration)`, `easeInOut()`. The game accepts camera commands only while the local player is an observer or a replay plays back.
- **Replay and observer control.** `pauseReplay`, `resumeReplay`, `setReplaySpeed`, `setReplayFastForward`, `replayControl(ReplayControlQuery)` (replay playback only, client-side pacing; the answer says when the speed was capped by the frame rate limit) and `observePlayer`, `observeNobody` (the observer's point of view).
- **`NotAllowedException`**, a subclass of `RequestFailedException`, for the new response status `NOT_ALLOWED`: the game refused the command because of the situation it is in. `RequestFailedException` is no longer final and has `reason()`.
- **Who moves the camera.** The `Camera` frame says what moved it (`change_source`), counts user camera actions (`user_input_count`), reports the lock in force (`follow_mode`, `follow_object_id`), why a lock made by a command ended (`follow_ended`, `follow_ended_object_id`) and whether a transition runs (`transition_active`). The app's camera line and the console `watch` output show it.
- **In-view statistics.** New frame `0x0B ViewStats` (`StatsListener.onViewStats`, `StateListener.viewStatsChanged`, `MatchState.viewStats()`): per player the value, effective value, class values and counts, veterancy counts, notable units (heroes and expensive units, with their portable add-on), superweapon timers, the value killed and lost and the damage per second over rolling windows, all for what is inside the camera's view. Default about 4 a second; `FeedConfig.view_stats_interval_ms`, `notable_cost`, `trade_window_ms`, `intensity_window_ms`.
- **Interest map.** New frame `0x0C InterestMap` (`onInterestMap`, `interestMapChanged`, `MatchState.interestMap()`), off until `FeedConfig.interest` is set: a grid of interest scores with decay, and the pending highlights (superweapon launches with target and impact frame, hero deaths, big structure losses).
- **`Director`**, with `DirectorLogic`, `DirectorConfig`, `DirectorMode`, `DirectorMove` and `DirectorClock`: an automatic camera director with the modes `HOTSPOT`, `HIGHLIGHTS`, `OVERVIEW` and `DIRECTOR`, minimum dwell, a switch threshold, pans for short and cuts for long distances, arrival before an impact, an overview tour of bases and armies in quiet times, and a pause when a human moves the camera. The decisions are pure (`DirectorLogic.poll(nowMillis)` on an injectable clock) and tested without threads or a game; `Director` is the shell that feeds them from a `MatchState` and sends the moves.
- New `FrameType` constants `VIEW_STATS` and `INTEREST_MAP`; new `StatsListener` and `StateListener` methods (all with empty defaults, so existing listeners compile unchanged). An exhaustive `switch` over `FrameType` must handle the two new constants.
- Hello capabilities: `camera.control`, `camera.follow`, `camera.source`, `replay.control`, `observe.player`, `view_stats`, `interest_map`, `status.not_allowed`.
- The test client logs the new frames in the Frames tab and keeps them in its state; the examples name the 2.1.0 jar. The GUI features for the new commands, a fake game for tests and the generated director examples came in 2.2.0.

## 2.0.0

For **protocol version 2** of the stats pipe. Breaking: a client of version 1.x cannot read a protocol 2 game, and this library refuses a game of protocol 1.

- **Breaking, the wire envelope.** Frames from the game now have a 17 byte little-endian header: `u32 body length | u8 type | u32 sequence | u64 timestamp_us`. Frames to the game keep the 5 byte header. `RawFrame` is now `(type, sequence, timestampMicros, body)` (the old two-argument constructor still exists for synthesized frames, with sequence 0 and timestamp 0); `DecodedFrame` has `sequence()` and `timestampMicros()` and `wireBytes()` counts 17 header bytes. The new frame types are `0x09 Hello` and `0x0A Response` from the game and `0x11 Request` to the game (`FrameType.HELLO`, `RESPONSE`, `REQUEST`).
- **Breaking, the handshake.** The first frame of a connection must be the game's `Hello` with `protocol_version` 2. `StatsPipe` waits for it (`helloTimeout`, 10 s by default) and refuses another version (`ProtocolVersionException`), another first frame (`FrameException`) and silence (`HelloTimeoutException`); the cause is passed to `onDisconnected`. New: `StatsPipe.hello()`, `awaitHello(Duration)`, `hasCapability(String)`, `StatsListener.onHello`, `MatchState.hello()` / `hasCapability`, `StateListener.helloReceived`, and the helper class `Handshake`.
- **Dropped frames.** The sequence numbers are checked on every connection (and on dump replays) with unsigned 32 bit arithmetic: `StatsPipe.droppedFrames()`, `MatchState.droppedFrames()`, `StatsListener.onFramesDropped(long)`, `StateListener.framesDropped(long, long)`. `ClockSync` (`StatsPipe.clockSync()`) estimates the offset between the game's frame clock and the local one and the extra delay of a frame; `Handshake.wallClockMillis` converts a timestamp with `Hello.epoch_unix_ms`.
- **Requests.** `StatsPipe.request(Request, Duration)` returns a `CompletableFuture<Response>` (ids assigned by the library, matched by id, `RequestTimeoutException` after the timeout, all pending requests fail with an `IOException` when the connection ends or the pipe closes, late and unknown responses ignored, no requests before the Hello). Typed methods: `catalog`, `object`, `objects`, `player`, `map`, `resync`, `feedConfig`, `setFeedConfig`, which fail with `RequestFailedException` (the `ResponseStatus` and the game's message) for any status but OK, and the paging helpers `catalogAll` / `objectsAll` (follow `next_cursor`, at most 100 pages, `PageLimitException`). The game rate-limits requests (`Hello.max_requests_per_second`, `max_request_burst`) and answers `RATE_LIMITED`; `StatsPipe.Builder.limitRequests(true)` applies the same limit on the client (off by default). New builder options `helloTimeout` and `requestTimeout`. `StatsListener.onResponse` sees every response.
- **Several readers.** The game serves up to `Hello.max_readers` readers per pipe; the library needs nothing for it, `reader_slot` and `max_readers` are in the Hello. The docs no longer say "one reader per pipe".
- **Dump files.** `DumpWriter` writes a header (magic `GOSD`, format version 2) and every frame with its sequence number and timestamp, the Hello included; `DumpReader` replays it and reports gaps as dropped frames. Dumps of format version 1 (no header, 5 byte envelope) are still read, with consecutive sequence numbers and timestamp 0. A dump of any other version is refused with a message saying so. `DumpWriter.FORMAT_VERSION` is 2.
- **Events.** The `StatEvent` message has `object_id`, `killer_object_id`, `killer_template` and `weapon` (generated classes); `Format.eventDetail` describes the killer and weapon of kills and losses.
- The test client shows the Hello (game version, protocol, reader slot of the maximum, logic rate) and the dropped-frame count in the GUI status area, prints `HELLO` and `DROPPED` lines in `watch` and `replay`, and adds `dropped N` to the `dump` status line. The `schema` command lists the new frames. The examples say the game serves several readers; their jar names are now 2.0.0.

## 1.0.0

First release of `com.generalsonline:stats-pipe-client`.

- The library (`lib/`): `StatsPipe` (builder, auto-discovery of running games preferring a free one, reconnect with backoff, an executor for the callbacks, `sendChat` with the documented limits), `StatsListener` (one method per frame type, lifecycle, errors), `MatchState` with `StateListener` change callbacks (players joined with MatchInfo, light/full snapshot merge, player state, match lifecycle, camera, world extent and map-level data, bounded event and chat buffers), `DumpWriter`/`DumpReader` with replay paced by game time, and the `Format` helpers. Generated protobuf classes come from the engine's `StatsExporter.proto`. Javadoc on every public type and member.
- The test client (`app/`), now written against the library's public API only: the commands `watch`, `dump`, `replay`, `chat`, `gui`, `schema` and the new `example`; the GUI with the tabs Players, Minimap, Events, Chat, Lobby, Match, Frames and the new Code tab.
- The example-code generator: eight scenarios (print every frame, track a player's stat, react to an event kind, draw the camera view box, show the lobby with predicted factions, send a chat line, record and replay a dump, use the state from a UI thread), filled with the selected Players column, event kind or chat channel. Each template is compile-checked, and the programs are in `examples/`.
- Changed from the earlier single-project client: the packages are `com.generalsonline.stats` (API), `.proto`, `.internal` and, for the client, `.app`; `FrameListener` became `StatsListener` (with `onFrame` instead of a frame tap), `StatsPipeClient` became `StatsPipe`, `DumpFile` became `DumpWriter` and `DumpReader`.
